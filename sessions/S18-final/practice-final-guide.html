Before anything: the mechanics that cost points

The exam is a Canvas quiz, auto-graded. Answers are compared as text, so formatting is correctness:

  • Comma-separated, no spaces. 2,3,5,8,9,6 — not 2, 3, 5, 8, 9, 6.
  • Ties break alphabetically / ascending unless the question says otherwise.
  • Read the determinism rule inside the question. Union-find and Huffman tie-breaking are stated per question precisely because the unstated version is ambiguous. A correct trace under the wrong tie rule is a wrong answer.
  • Give what is asked for. “The FINAL row” means one row, not the table. “The pivot’s index” means a number, not the array.
  • 0-based or 1-based is always stated. Q3 says 0-based; Q13 says write the heap array 1-indexed. Both appear on the same exam on purpose.

Budget roughly one minute per point, which leaves ten minutes of slack. Q1 is 10 points of recall with no computation — do it first, bank the points, and let the tracing questions have the time.

Q1 — Tight complexity bounds (10 pts)

What it tests. Whether you know the cost of each algorithm and what the variables mean. The word tight matters: a true-but-loose bound is wrong.

The method For each item ask two questions in order: (1) what does the algorithm actually do, in one phrase? (2) what is the input it does it to? Most wrong answers here come from answering (1) correctly and (2) not at all.
#ItemAnswerThe phrase that produces it
1Kruskal, edges unsorted\(O(E\log V)\)sort the edges — \(E\log E\), and \(\log E \le 2\log V\)
2Huffman, binary min-heap\(O(n\log n)\)\(n-1\) merges, each two pops and a push
3KMP search\(O(n+m)\)preprocess the pattern, then read the text once
4Fill the LCS table\(O(nm)\)one constant-time cell per pair of prefixes
5quickselect, average\(O(n)\)partition, then recurse on one side: \(n + n/2 + n/4 \to 2n\)
6AVL worst-case search\(O(\log n)\)height is bounded by \(\approx 1.44\log n\)
7Find the min in a min-heap\(O(1)\)it is the root — just look at it
8union, weighted + path compression\(O(1)\)\(\alpha(n)\), “effectively constant”
9Build the KMP failure functionsee the warningmatch the pattern against itself — \(\Theta(m)\)
10Comparison-sort lower bound\(O(n\log n)\)\(\log_2(n!)\) leaves in the decision tree
Where people go wrong
  • #1 → O(E + V) — that is Kruskal after someone else sorted the edges. “Edges unsorted” is exactly the clause that puts the sort inside your cost.
  • #1 → O(V²) — that is Prim with an array scan for the minimum. Different algorithm.
  • #2 → O(n) — counting the merges (\(n-1\)) but not what a merge costs. Each does two delMins and an insert.
  • #2 → O(n²) — that is Huffman with a linear scan for the two smallest. The question names the min-heap; the data structure it names is load-bearing.
  • #3 → O(nm) — that is brute force. The entire content of KMP is that this does not happen.
  • #5 → O(n log n) — the commonest error on this bank. Quicksort recurses on both sides; quickselect on one. If you cannot recall which, re-derive it: \(n + n/2 + n/4 + \dots = 2n\) is faster to reconstruct than to memorize.
  • #6 → O(n) — that is a plain BST, which an AVL exists to prevent. A linear answer for a balanced structure means you answered for the unbalanced one.
  • #7 → O(log n) — you answered delete-min. Finding it is free; removing it costs the sink. Read the verb.
  • #8 → O(log n) — that is weighted quick-union without path compression. The question names the optimization, so it wants the optimized bound.
  • #10 → O(n) — confusing the comparison lower bound with counting sort, which beats it by not comparing. The bound binds only algorithms whose sole tool is comparison.
⚠ Two defects in this question, flagged honestly

#9 is keyed \(O(n+m)\), but building the failure function touches only the pattern — Lecture 16 says \(\Theta(m)\) three times and Chapter 16 agrees. \(O(n+m)\) is a true upper bound but not a tight one, and this question demands tight bounds. The option list contains no \(O(m)\), so no tight answer is available. Enter \(O(n+m)\) to match the key, and know that the honest answer is \(\Theta(m)\): the build never looks at the text.

#10 asks for a lower bound, which is properly \(\Omega(n\log n)\), not \(O\). The option list is all-\(O\), so enter \(O(n\log n)\) — but write \(\Omega\) on paper and in your head. Both items have been reported for correction.

Q2 — Union-find & Kruskal (10 pts)

(a) Weighted quick-union with full path compression

What it tests. Whether you can execute a data structure exactly as specified, including the parts that are easy to skip.

The method Keep parent[] and size[]. For each union(p,q):
  1. find(p) and find(q) — and these compress. This is the step people skip.
  2. Compare the roots’ sizes (not heights, not depths — the question says size).
  3. Larger root wins; the smaller tree’s root points at it, and the winner’s size grows by the loser’s.
  4. On a tie, the question’s rule: p’s root goes under q’s root.
The answer find(1) = 3, find(7) = 7, and parent[] = 3,3,3,3,5,7,7,7,9,3 
  the four small unions all hit the size tie:
     parent[0]=1  parent[2]=3  parent[4]=5  parent[6]=7
  union(0,2)  ties at size 2 → parent[1]=3
  union(4,6)  ties at size 2 → parent[5]=7
  union(8,9)                 → parent[8]=9
  union(0,8)  find(0) walks 0→1→3 AND COMPRESSES 0 straight to 3;
              size 4 beats size 2 → parent[9]=3
Where people go wrong
  • Forgetting that union compresses. union(0,8) calls find(0), which repoints 0 directly at 3. Compress only during the two explicit finds at the end and you get parent[0]=1 — one slot wrong, whole answer wrong. Every find compresses, including the ones inside union.
  • Getting the tie backwards (parent[q_root] = p_root). Four of the eight unions are ties here, so this one misreading corrupts most of the array.
  • Linking by height instead of size. They agree for a while and then diverge. The question defines tree size.
  • Reporting the array before the final finds. Here find(1) and find(7) happen to change nothing — 1 already points at 3, and 7 is a root — but verify that rather than assume it.
  • Expecting one component. The final array has 3 and 7 as roots; the sequence never unions them. “It must all be connected” is an assumption, not a given.

(b) Kruskal

The method Sort edges by weight ascending. Walk the list; accept an edge iff its endpoints are in different components; stop after \(V-1 = 8\) accepted edges.
The answer accepted 2-8,7-6,0-1,5-6,7-8,2-3,1-2,3-4 · first skip 4-5 · weight 36
Where people go wrong
  • Listing the accepted edges in graph order. The question says “in the order Kruskal accepts them”, which is weight order. Problem-statement order scores zero on a string match.
  • Leaving the skip blank because the MST was already complete. After 8 accepts every vertex is joined, so the next edge (4,5,9) is rejected — that is the first skip, and it necessarily comes after some accepts.
  • Summing all twelve weights. The MST weight is the sum of the accepted eight: \(1+2+3+4+5+6+7+8 = 36\).
  • Sorting by vertex label. Kruskal is greedy by weight; nothing else orders the list.
Practise it live Union-find shows the tree flattening as compression fires — the step this question is really about — and Kruskal highlights each edge as it is accepted or rejected, with the running MST weight.

Q3 — Quicksort partition & selection (8 pts)

The method Pivot is the last element (5). Set i = -1. Scan j from the left up to the element before the pivot; whenever a[j] < pivot, increment i and swap a[i] with a[j]. At the end swap a[i+1] with the pivot. 
  6,9,2,8,3,5   pivot 5, i = −1
  j=0: 6<5? no          j=1: 9<5? no
  j=2: 2<5? yes → i=0, swap a[0],a[2] → 2,9,6,8,3,5
  j=3: 8<5? no
  j=4: 3<5? yes → i=1, swap a[1],a[4] → 2,3,6,8,9,5
  end: swap a[2],a[5]                 → 2,3,5,8,9,6
The answer (a) 2,3,5,8,9,6 · (b) pivot index 2 · (c) done · (d) 5
Where people go wrong
  • Forgetting the final swap. Stopping at 2,3,6,8,9,5 leaves the pivot at the end — the partition has not happened. The pivot’s whole job is to reach its sorted position.
  • Using <= instead of <. Changes which elements move and, with duplicates, the pivot’s final index. Use the comparison the question writes.
  • Partitioning around the first element. A valid convention this question does not use — that is Hoare’s scheme from L13. Do not mix the two.
  • Answering (c) “recurse left”. The 3rd smallest sits at 0-based index 2, and the pivot landed at index 2. They coincide, so the search is done. The comparison is \(k-1 = \text{pivotIndex}\), and that off-by-one is exactly what the question probes.
  • Answering (d) with 3. The value at index 2 is 5. Check it against the sorted array 2,3,5,6,8,9 — third element, 5.
Practise it live Quicksort steps the Lomuto partition with i and j highlighted; Quickselect shows the one-sided recursion, which is also the answer to Q1 #5.

Q4 — Huffman coding (8 pts)

The method Repeatedly merge the two lowest-frequency nodes. Both rules matter: which two to merge — lowest frequency, ties to the node whose alphabetically-first contained symbol comes first; and which becomes the 0 (left) child — the smaller of the two, by that same rule. 
  g3 f4                   → gf7      (g left)
  c7 gf7   tie → c first  → cgf14    (c left, so c=…0, g=…10, f=…11)
  b12 cgf14               → bcfg26   (b left)
  e14 a25                 → ae39     (e left)
  bcfg26 d28              → bcdfg54  (bcfg left)
  ae39 bcdfg54            → root 93  (ae left)
The answer a=01 · c=1010 · d=11 · f=10111 · g=10110
fade = 10111 + 01 + 11 + 00 = 10111011100, 11 bits
Two sanity checks before you commit Sort your symbols by frequency; the code lengths must not increase: 
  d 28 → 2 bits    a 25 → 2    e 14 → 2    b 12 → 3
  c  7 → 4         f  4 → 5    g  3 → 5
If a frequent symbol ends up longer than a rare one, you merged wrong. Second: no code may be a prefix of another — scan your five answers for that before writing them down.
Where people go wrong
  • Ignoring the tie rules. The c7 vs gf7 tie is placed deliberately. Break it the other way and every code below it changes. The answer is not “a valid Huffman tree”, it is the tree the rules produce.
  • Swapping 0 and 1. Also yields an optimal code with the same lengths — and is still marked wrong, because the question fixes the convention so the answer is unique.
  • Reading codes leaf-to-root. Codes are read from the root down; the other direction gives every code reversed.
  • Counting bits as symbols. fade is four characters but 11 bits — the entire point of a variable-length code. Add the code lengths: \(5+2+2+2\).
  • Encoding in sorted order. fade is f, a, d, e — not a, d, e, f.
Practise it live Huffman takes your own frequencies (SYM-FRQ(a:25, b:12, …)), builds the trie merge by merge, and reports the codes — the fastest way to check a tie-break by hand against a machine.

Q5 — Recurrences (6 pts)

The method For \(T(n) = a\,T(n/b) + f(n)\), compute \(n^{\log_b a}\) and compare it to \(f(n)\): if \(n^{\log_b a}\) is bigger → case 1, \(\Theta(n^{\log_b a})\); equal → case 2, multiply by \(\log n\); \(f(n)\) bigger (and regular) → case 3, \(\Theta(f(n))\).
The answer
  1. \(2T(n/2)+1\): \(n^{\log_2 2}=n\) vs \(1\) → case 1, \(\Theta(n)\)
  2. \(T(n/2)+1\): \(n^{\log_2 1}=1\) vs \(1\) → case 2, \(\Theta(\log n)\)
  3. \(3T(n/2)+n\): \(n^{\log_2 3}\approx n^{1.58}\) vs \(n\) → case 1, \(\Theta(n^{\log_2 3})\)
Where people go wrong
  • Comparing \(a\) to \(b\). The comparison is between \(n^{\log_b a}\) and \(f(n)\), never between the constants.
  • #1 → Θ(n log n) — pattern-matching to mergesort, which is \(2T(n/2)+n\). Here \(f=1\), so the leaves dominate instead of the levels sharing equally. That difference is case 1 versus case 2.
  • #2 → Θ(1) or Θ(n) — this is binary search: constant work per level, \(\log n\) levels, and the answer is their product.
  • #3 → Θ(n log n) — only correct if the two sides were equal, and \(1.58 > 1\). Leave the answer as \(n^{\log_2 3}\); that is the answer, not an unfinished one.
  • Giving the case without the bound, or the bound without the case. The question asks for both.
Practise it live Master theorem draws one bar per recursion-tree level: growing bars mean case 3, flat means case 2, shrinking means case 1. Type any of the three and read the case off the shape.

Q6 — LCS (8 pts)

The method Rows are A = ABDCBA, columns B = BDACB, with an ε row and column of zeros. Match → diagonal + 1; mismatch → max(up, left). 
       ε  B  D  A  C  B
  ε    0  0  0  0  0  0
  A    0  0  0  1  1  1
  AB   0  1  1  1  1  2
  ABD  0  1  2  2  2  2
  ABDC 0  1  2  2  3  3     ← the row asked for
  ABDCB 0 1  2  2  3  4
  ABDCBA 0 1 2  3  3  4     ← the final row
The answer row ABDC = 0,1,2,2,3,3 · final row = 0,1,2,3,3,4 · length 4 · e.g. BDCB
Where people go wrong
  • Omitting the ε column. The question says “its 6 values, ε-column first”. Five values is an automatic zero even when the numbers are right.
  • Counting the wrong row. “The prefix ABDC” is row 4 — the row after four characters. Label your rows with the prefix, not a number.
  • Adding 1 on a mismatch. Only a match adds. A mismatch inherits the better neighbour unchanged; the table never grows on a mismatch.
  • Taking the max of the wrong pair. The mismatch case is max(up, left) — never the diagonal. The diagonal is for matches only.
  • A traceback that is not a subsequence. Verify before writing: BDCB must appear in order (not contiguously) in ABDCBA and in BDACB. Any valid LCS of length 4 is accepted, so check rather than guess.
  • Assuming the LCS is unique. It need not be; the length is.
Practise it live LCS fills this exact table cell by cell — type ABDCBA and BDACB — and the green traceback spells a valid answer. For why the recurrence is what it is, the LCS recursion tree shows the exponential search the table replaces.

Q7 — 0/1 knapsack (7 pts)

The method K[i][w] = max(skip = K[i-1][w], take = value[i] + K[i-1][w - weight[i]]), with “take” available only if the item fits. Fill row by row; the final row is item 4’s. 
  items (v/w):  1: 40/1   2: 80/2   3: 100/3   4: 60/2      W = 5
  after item 1: 0,40,40,40,40,40
  after item 2: 0,40,80,120,120,120
  after item 3: 0,40,80,120,140,180
  after item 4: 0,40,80,120,140,180     ← the final row
The answer final row 0,40,80,120,140,180 · optimal 180 · e.g. {2,3} (weight 5) or {1,2,4} (weight 5)
Where people go wrong
  • Reading the same row for “take”. It must read K[i-1][…] — the row above. Reading K[i][…] lets you take an item twice, which is unbounded knapsack: a different problem, and the difference is exactly this index.
  • Going greedy by value-per-weight. The ratios are 40, 40, 33.3, 30, and greedy happens to reach 180 on this data — which is luck, not method. L15 breaks it in one slide. Fill the table.
  • Forgetting the fit check and computing K[i-1][negative].
  • Giving the whole table when one row is asked for, or the row without the \(w = 0\) entry.
  • Assuming the optimal set is unique. Two different sets reach 180; either is accepted.
Practise it live 0/1 knapsack fills the take-or-skip table with both source cells highlighted, then traces back the chosen items. Change \(W\) and watch the answer set change — at \(W=12\) the densest item drops out entirely, which is why greedy has no licence here.

Q8 — KMP & tries (8 pts)

(a) The failure function of ababab

The method fail[j] is the length of the longest proper prefix of P[0..j] that is also a suffix of it. Build it by matching the pattern against itself: fail[0] = 0; then for each j, if P[j] == P[k] the overlap grows, otherwise fall back to k = fail[k-1] and retry.
The answer 0,0,1,2,3,4
Where people go wrong
  • 0,1,2,3,4,5 — forgetting proper. fail[j] can never equal \(j+1\); the whole string is not a proper prefix of itself. If your last value equals the pattern length, this is the error.
  • Starting at fail[0] = 1. A single character has no proper prefix, so it is always 0.
  • Giving the DFA table instead. L16 shows both views; this asks for the failure function, one value per position.

(b) The trie

  s ─ u ─ n ─ g          nodes (excluding root): s,u,n,g,k,a,d,i,p = 9
    │       └ k          depth: root→s→u→n→g = 4
    ├ a ─ d
    └ i ─ p
The answer 9 nodes · depth 4 · su is not a stored word
Where people go wrong
  • Counting the root (10) when the question says not to.
  • Counting words (5), or counting characters across all words (17) — which misses that sun, sung and sunk share the s-u-n path. Prefix sharing is the whole reason a trie is compact.
  • su → “yes, it’s in there”. The path exists, on the way to sun; the word-end flag is false. This is the most-tested trie idea in the course and the commonest bug in ICA 16.
Practise it live Building fail[] constructs the table cell by cell, including the fall-back chain — run ababab. Trie takes your own word list; search sun then su to see the word-end flag decide.

Q9 — Hashing (7 pts)

The method \(\text{conv}(x) = \text{length}(x) + \sum \text{ord}(c)\) with a = 1 … z = 26; \(h = \text{conv} \bmod 7\); collisions probe forward, wrapping 6 → 0. 
  ml  = 2 + (13+12) = 27 → 27 mod 7 = 6
  ai  = 2 + (1+9)   = 12 → 5
  db  = 2 + (4+2)   = 8  → 1
  os  = 2 + (15+19) = 36 → 1
  ux  = 2 + (21+24) = 47 → 5
  api = 3 + (1+16+9)= 29 → 1

  insert in order:
    ml→6 · ai→5 · db→1 · os→1 taken→2 · ux→5,6 taken, wrap→0 · api→1,2 taken→3
The answer homes 6,5,1,1,5,1 · table ux,db,os,api,_,ai,ml
Where people go wrong
  • Dropping the length(x) term. It is in the definition precisely to catch reading past it. Without it every home slot shifts.
  • Using ASCII. ord(a) = 1, not 97. The question defines its own mapping.
  • Not wrapping. ux probes 5, 6, then 0 — the table is circular. Stopping at 6 and declaring it full loses the rest.
  • Probing from the wrong start. Each key probes from its own home slot, not from where the previous key landed.
  • Inserting in a different order. The given order produces this table; sorting the keys first produces a different, wrong one.
  • Reporting homes after probing. (a) asks where each key hashes, (b) where it ends up. os homes to 1 and lands at 2 — both are on the page and they are different answers.
Practise it live Hash table (linear probing) animates the probe walk and the wrap; watch how one cluster makes the next insertion longer, which is also the answer to Q10(a).

Q10 — Design (6 pts)

What it tests. Whether you can match a structure to a query type and say why — the course’s through-line, not a fact to recall.

A full-credit shape

(a) At high load factor, separate chaining degrades gracefully: buckets lengthen, a search scans a chain, cost is \(\Theta(\alpha)\), and \(\alpha > 1\) is legal. Linear probing degrades sharply: clusters merge and grow, so each insert both takes longer and makes the next cluster bigger; as \(\alpha \to 1\) the probe count explodes, and the table cannot exceed \(\alpha = 1\) at all. Deletion is also harder under probing — you cannot blank a slot without breaking the probe chains through it (tombstones, or reinsert the cluster).

(b) Date ranges → a balanced BST / B+ tree: it keeps keys in order, so a range query is “find the low end, then walk in order to the high end” — output-sensitive, no full scan. Title prefixes → a trie: a prefix is a path from the root, and every completion is exactly the subtree beneath it.

Where people go wrong
  • Naming a hash table for the range query. The most common wrong answer, and the reason is worth saying: hashing deliberately destroys order, so neighbouring keys land in unrelated buckets and a range means scanning everything. The property that makes it fast for point lookups is the property that makes it useless here.
  • Naming a BST for the prefix query. Not worthless — an ordered structure can find a prefix range — but a trie is better and the justification is the discriminator. Say why: prefix = path, completions = subtree.
  • Defining chaining and probing without answering “where do they degrade”. The question asks about behaviour under load.
  • Claiming chaining “never degrades”. It does — \(\Theta(\alpha)\) per search. The contrast is graceful versus sharp, not immune versus fragile.

Q11 — Regular expressions (6 pts)

The method Build from the four operations only: concatenation, |, *, (). Then test your answer against three strings: a typical member, a boundary member, and a near-miss non-member.
The answer (1) (a|b)(a|b) · (2) (0|1)*0. Equivalents accepted.
Where people go wrong
  • (1) → (a|b)* — accepts every length including 0 and 1. “Exactly two” means concatenate two choices, not star them.
  • (1) → ab — one specific string, not the four (aa, ab, ba, bb).
  • (2) → 1*0 — rejects 00, which does end in 0. Anything may precede the final 0, including more 0s.
  • (2) → (0|1)*0* — accepts 01, which does not end in 0, and accepts the empty string. The final 0 must be mandatory and last.
  • (2) → (0|1)* — accepts everything.
  • Reaching for {2}, +, ?, \d. Sugar, and fine if equivalents are accepted — but the exam tests the four primitives, so be sure you could expand whatever you write.

Q12 — DFA (10 pts)

The method Ask what the machine must remember. “Even number of a’s” needs one bit — the parity so far — so two states suffice, and b never changes it. 
  → S0 (accepting) | a → S1 | b → S0
    S1             | a → S0 | b → S1
The answer The table above, and: aa Yes · aba Yes · b Yes · abab Yes · a No · baab Yes · bb Yes · ε Yes
Where people go wrong
  • Making S0 non-accepting. Zero is even, so the empty string is accepted and the start state must accept. Seven of the eight test strings depend on this — every one except a.
  • ε → No. The same error in its purest form. If you got ε wrong you almost certainly got b and bb wrong too; they are one fact.
  • Sending b to the other state. Only a flips parity. A b self-loops.
  • Building four states, one per a/b combination. Not wrong, just unnecessary — and more states mean more chances to mis-fill the table. Remember only what must be remembered.
  • Forgetting to mark the start state. Six of the ten points are the table, and the start marker is part of it.
  • Mis-counting the a’s. baab has two → Yes. These four points are free.
Practise it live DFA runs exactly this kind of machine — pick even-As and feed it the eight test strings; one highlighted state is the machine’s entire memory. Then the NFA simulator for the contrast: a whole set of states at once.

Q13 — Binary heap (3 pts)

The method Append at the end, then swim: while the node beats its parent, swap up (parent of i is i/2, 1-indexed). For delMax: the root leaves, the last element moves to the root, then sink — swap with the larger child while it beats you. 
  12               → 12
  19  swims        → 19,12
  6                → 19,12,6
  24  swims twice  → 24,19,6,12
  10               → 24,19,6,12,10
  28  swims twice  → 28,19,24,12,10,6
  8                → 28,19,24,12,10,6,8
The answer (a) 28,19,24,12,10,6,8 · (b) 24,19,8,12,10,6
Where people go wrong
  • 0-indexing. The question says 1-indexed; with 0-indexing the parent is (i-1)/2 and your swim targets shift. The contents can be right while the answer string is wrong.
  • Sorting the array. A heap is not sorted — it satisfies only parent ≥ child. 28,19,24,… is correct and is not descending.
  • On delMax, promoting the larger child repeatedly. That leaves a hole in the middle and an array of the wrong shape. Last element to the root, then sink.
  • Sinking against the wrong child. Swap with the larger of the two, or you break the heap property with the other one.
  • Forgetting the array shrinks. After delMax there are six entries, not seven.
Practise it live Binary heap (max) shows the swim and sink paths on both the tree and the array — insert 12,19,6,24,10,28,8 and then delete the max.

Q14 — Dijkstra (3 pts)

The method All distances ∞ except the source at 0. Repeatedly finalize the unfinalized vertex with the smallest tentative distance, then relax its outgoing edges. 
  finalize 0 (0):  dist[1]=1, dist[2]=6
  finalize 1 (1):  0+1+2 = 3 < 6 → dist[2]=3 ;  dist[3]=1+9=10
  finalize 2 (3):  3+3 = 6 < 10  → dist[3]=6
  finalize 3 (6):  dist[4]=7
  finalize 4 (7)
The answer 0,1,3,6,7
Where people go wrong
  • Leaving dist[2] = 6. The direct edge 0→2 costs 6, but 0→1→2 costs 3. Taking the first value you write and never improving it is the classic Dijkstra error — relaxation exists to overwrite it.
  • Leaving dist[3] = 10. The same error one step later: 1→3 gives 10, 2→3 gives 6.
  • Relaxing from a vertex before it is finalized. Process vertices in order of finalized distance; that ordering is what makes the algorithm correct with non-negative weights.
  • Treating the graph as undirected. The edges are directed — there is no 2→0 or 3→1.
  • Reporting the path instead of the distances.
Practise it live Dijkstra shows each relaxation overwriting a tentative distance — exactly the step this question punishes you for skipping.

The five errors that cost the most points

  1. Ignoring a stated determinism rule (Q2 and Q4 tie-breaking). Your trace can be flawless and still wrong. Read the rule, and re-read it before you commit.
  2. Answering the wrong verb. find-min vs delete-min (Q1 #7), homes vs final slots (Q9), value vs index (Q3), path vs distances (Q14).
  3. Off-by-one between an ordinal and an index. “3rd smallest” is index 2 (Q3); “the prefix ABDC” is row 4 (Q6); 1-indexed heaps (Q13).
  4. Not improving a first estimate. Dijkstra’s dist[2] (Q14) and the mismatch branch in LCS (Q6) both punish taking the first number you wrote.
  5. Formatting. Comma-separated, no spaces; exactly what was asked for; the ε column included. Free points, lost every term.
